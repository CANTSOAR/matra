# Threat model

Status: draft by the author, written from reading the code. Not reviewed by an outside cryptographer. Not audited. Update it with every security-relevant change.

**This is a supplement to the [Security Whitepaper](SECURITY_WHITEPAPER.md), which is the primary description of the architecture, key hierarchy, ledger and threat model.** This file is the engineering tracker of known weaknesses (W1 to W22). Where the two disagree, the whitepaper and the code win; fix this file.

## 1. What is protected

| Asset | Where it lives |
|---|---|
| Record contents and attachments | Encrypted in the browser (AES-256-GCM); server stores ciphertext only |
| Passphrase and master key | Browser memory only. The server receives a separate derived `authKey`; with a recovery code (W20), the master key also exists on the server wrapped under keys only her passphrase or her code can derive |
| Per-record keys | Wrapped by the master key; re-wrapped to an attorney's RSA-OAEP public key on sharing |
| Sealed-match identifiers (perpetrator email, phone, social profile; never names) | Canonicalised in the browser, then mapped through a t-of-m threshold RFC 9497 VOPRF (key Shamir-shared among holders 1..m, default 2-of-3) to a pseudorandom tag. The server stores the tag, a contact bundle encrypted under a per-perpetrator key, and Shamir shares sealed to counselors. Not private from someone holding **t** key shares (W2, W14) |
| Matched survivors' contact preferences | Openable only by a verified counselor holding two survivors' shares for the same tag (whitepaper §4a). Staged release: the summary (identifier, states, contact *methods*) opens first; the contact *details* are a separate ciphertext the server withholds until the assigned counselor records a conflict check (W21) |
| A matched survivor's full report | Released only by her own yes to a counselor's request: her record key is wrapped to that one counselor's RSA key on her device (W21) |
| Integrity history | Append-only SHA-256 hash-chain ledger, enforced by SQLite triggers |

## 2. What the operator can still see

Zero-knowledge covers content, not metadata. A server operator, database thief or a party with a subpoena can see:

- Usernames, roles, account creation time, and the sign-in time of each live session (session rows are deleted within
  about 10 minutes of their 12 h expiry, or at logout, so there is no history of past sign-ins). **Not IP addresses or
  user agents** (W11): Matra's code never writes them to the database, ledger or logs; per-client rate limits hold
  only a daily-salted HMAC of the IP, in memory, and a timer drops the salt and those keys at midnight UTC. The hosting provider's edge (and an operator who modifies the server) can still see them.
  Field-by-field list with retention: [PRIVACY_DATA_INVENTORY.md](PRIVACY_DATA_INVENTORY.md).
- Number, size and timestamps of records and attachments.
- Which survivor shared with which attorney, when, and the consent statement text (hashed in the ledger; stored in the share record).
- Attorney profiles (name, organization, bar number, jurisdictions).
- Sealed-match tags: which entries name the same (unknown) person, cluster sizes even below the threshold, and whether and when a group matched. (Survivors never see match state; attorneys no longer see counts; each matched group goes to the one verified counselor the matcher assigned it to.)
- For each released group, which counselor the matcher assigned it to and why (the reason names one state, e.g.
  `incident_state:NY`). Per-entry states are sealed to the matcher and never stored readable by the app server; the
  matcher's own database holds them in clear, next to tags and pseudonymous survivor references (W18).
- OPRF quota counters per account (today's count and a lifetime total), and counselor outreach-note counts and times (note contents are encrypted to the counselor).
- Staged release: when the assigned counselor recorded her conflict check for a group and its result; each report
  request (group, entry, counselor, status, times); and for each yes, a release row naming the survivor, the counselor,
  the record, the consent text and when it was first opened or revoked (the report itself stays ciphertext wrapped to
  the counselor). Joined with `match_entries.user_id`, the operator can see which accounts a counselor asked (W21).
- Whether an account has confirmed a phone for sealed matching (`users.matching_verified`), and a table of keyed phone
  hashes with a count each (`phone_tokens`, no account id, written in a separate later batch). For up to 10 minutes
  during a verification, the number is in the app server's memory. The SMS provider (Twilio in production) sees the
  number and when it was verified; its records together with Matra's activity records (e.g. when the account first
  sealed an entry) could link the number to the account (W19).

Never describe the system as "mathematically impossible to hand over data." Say: *the operator cannot decrypt record contents. The survivor and anyone she shared with still can be compelled, and metadata is producible.*

## 3. Adversaries

| Adversary | Goal |
|---|---|
| Abuser or associate with access to the survivor's device or accounts | Read records, learn she is documenting |
| Abuser using the platform | Learn whether he has been reported (escrow probing); impersonate an attorney |
| Network attacker | Intercept or modify traffic |
| Database or backup thief | Read data, brute-force passphrases offline |
| Malicious or compromised operator or insider | Read data, substitute keys, silently alter the web client |
| Legal process (defense subpoena, law enforcement) | Compel the operator, survivor or attorney |
| Malicious or careless attorney | Leak or misuse shared records |
| Malicious or careless counselor | Misuse matched survivors' contact details; try to open unmatched entries |
| OPRF key holder(s), or someone who obtains both key shares | Test guessed identifiers; tag or block users with wrong evaluations |
| Sybil attacker | Create accounts to force a "match" on a target and expose a real survivor's contact bundle |

## 4. Known weaknesses (fix before real data)

Severity: **High** = blocks any real use.

| # | Weakness | Sev | Notes / planned fix |
|---|---|---|---|
| W1 | **Match probing.** *Fixed for survivors and attorneys:* `/api/matching/entries` and `/api/escrow` always return `sealed` with no match time or tag; nothing in a survivor's audit log mentions a match or a counselor; no ledger entry at match time (ledger grows by exactly one per submission); the match insert is one always-executed statement. Attorneys no longer receive match counts (`ShareBundle.escrow` removed). Matched groups go only to verified counselors. **Residual:** a counselor contacting a perpetrator whose fake entry matched reveals the match. Staged release adds a second, smaller one: a report request is shown to the survivor in her own space, so it tells her that her entry matched; the counselor may only send one after ticking that she has already spoken with her and she expects it, so the request is never the first sign (a server-side tick, not a proof). | Low–Med | Counselor plausibility review before contact; never confirm who else was named; delayed/batched release could be added. |
| W2 | **Low-entropy identifiers.** Phone numbers have ~10^10 values. *Addressed by design:* tags need VOPRF_k with k Shamir-shared t-of-m (default 2-of-3); a DB thief can't test guesses, and each API guess costs one unit of the account's budget, charged by the app server once per distinct blinded element whichever holders it goes to (≤ 10/day, ≤ 50 lifetime per verified-adult survivor account; each holder also counts its own calls as a backstop). Without that account-level charge an account could send each guess to a different t-subset of holders and get ⌊m·L/t⌋ guesses (fixed; regression test in `apps/server/src/matching.test.ts`). These limits bind survivor accounts through an honest app server, not the operator (W14). *Key custody (security review M3, fixed):* production refuses to start unless every share comes from the environment or files outside the DB directory (or the holders are remote processes), and never auto-generates them, so a DB volume copy holds none. **Residual:** whoever holds **t** shares can brute-force offline in milliseconds per thousand guesses (W14; regression tests `apps/server/src/config.test.ts`, `packages/crypto/src/threshold.test.ts`). | Med (was High) | Holders at independent institutions (remote mode); DKG instead of a dealer; HSM/KMS custody; monitoring of evaluation volume. |
| W3 | **Attorney key substitution.** The client fetches attorney public keys from the server (`GET /api/attorneys`). A malicious or compromised operator could substitute its own key and receive shared record keys. *Mitigated (weekend MVP):* the organization signs an **attorney directory** offline (each verified attorney's id, name, organization, `status: verified` and RSA key fingerprint; `packages/crypto/src/directory.ts`) with the **same org Ed25519 key that signs the counselor roster** (W15), under its own domain prefix (`matra/attorney-directory/v1|`), so a roster signature can't be replayed as a directory signature. It is signed by `sign-roster` or by `verify-attorney` given the key (`apps/server/src/org-signing.ts`), stored by the server and served with `GET /api/attorneys`. Builds pin the org key (`MATRA_COUNSELOR_ROSTER_PUBKEY`); her client checks each attorney's key against the signed directory on her device and shows *"Verified by Matra: this key belongs to …"* with the signed name; a swapped key, an unlisted attorney, or an unsigned or forged directory turns sharing off (tests: `packages/crypto/src/directory.test.ts`, `apps/server/src/shares.test.ts`, demo e2e 2b). There is no manual step: the fingerprint is an optional, collapsed *Check it yourself* detail and she is never asked to contact the attorney. The fingerprint stays in the consent statement and is still checked by the server against the key on file. **Residual:** (1) everything rests on the org signing key and on whoever holds it vetting attorneys (W7): a stolen or misused org key can list any key; it must stay offline, with the person who verifies; (2) one org key signs both lists, so its compromise affects counselors and attorneys alike (a separate pinned key would split that, at the cost of a second key ceremony and build pin); (3) there is no transparency log, so the org could sign a targeted directory for one survivor and nobody else would see it; (4) **unpinned builds** (development and `MATRA_DEMO_MODE=1` demo builds without `MATRA_COUNSELOR_ROSTER_PUBKEY`) trust the server's key, labelled *"Development version"* on the share screen, with no manual fallback; a production build that is not a demo refuses to build without the pin, and its share screen treats an unpinned key as not shareable (`vite.config.ts` `assertProductionPins`, `matchPins.ts` `attorneyShareable`; test `apps/web/src/build/matcherPins.test.ts`); (5) between a verification and the next signing run a new attorney shows as "can't confirm", and a revoked attorney stays in the signed directory until re-signed (the server stops listing them, sharing to them and serving them existing shares at once, and signs them out, but a malicious server could ignore that); (6) the malicious-client problem (W4) is untouched. The label *"Verified by Matra"* is a representation about an attorney: legal questions Q-001 and Q-053. | Med (was High) | Key transparency: publish each signed directory to an append-only log her client checks (and that attorneys can monitor for their own entry); signed expiry on directories; consider a separate pinned key per list; the vetting procedure in W7. |
| W4 | **The operator ships the client code.** A compromised server can serve a modified web app that exfiltrates the passphrase. Zero-knowledge from the server doesn't protect against this. | High | Reproducible builds, subresource integrity, a native or extension client with signed releases, and publishing build hashes. Independent hosting of the client. |
| W5 | **Passphrase strength and offline attack.** Keys derive from a passphrase via PBKDF2-SHA256 (600k; her client refuses a lower count from the server's prelogin, and a production server refuses to register one). A stolen database enables offline guessing of weak passphrases. Key version 2 (an account with a recovery code, W20) does not change this: the passphrase still derives the auth key and KEK_pass through the same PBKDF2, so a guessed passphrase unwraps the account secret. The recovery code is **not** passphrase-derived: it is 128 random bits from the CSPRNG, so it is not stretched (stretching adds nothing to 128 bits of entropy) and is out of reach of offline guessing. *Account deletion is not a crypto-shred:* it deletes her ciphertext and wrapped keys from the live database (`secure_delete` on, then a TRUNCATE checkpoint), but a backup or copy of the database made earlier still holds them, wrapped under keys only her passphrase (or her recovery code) derives, so the same offline guessing applies to a deleted account in an old backup. | Med | Move to Argon2id for the passphrase (needs a WASM dependency) and enforce passphrase strength (generated diceware recommended). Nobody but she can reset a passphrase: without a recovery code it can't be reset at all, by design. Say so plainly. |
| W6 | **Shares never expire.** *Fixed (expiry):* every share has `expires_at` (default 90 days, survivor-selectable 1 to 365 days, set in the consent statement and the `share.granted` ledger hash). The bundle route and evidence download return 403 `share_expired` after that time. `POST /api/shares/:id/renew` extends it and writes a `share.renewed` ledger entry and audit rows; the dashboard shows expiry and offers renewal. Existing rows were migrated to created_at + 90 days. **Residual:** expiry and revocation stop future access only; content already decrypted by the attorney cannot be clawed back (stated in the consent text). | Low | Keep telling survivors this plainly; partner terms on attorney-side retention. |
| W7 | **Attorney verification is a manual flag** (`verify-attorney.ts`). No defined vetting process, so someone could pose as an attorney. *Unverifying works at once:* `--revoke` deletes the attorney's sessions, and the share list, bundle and evidence routes refuse an unverified attorney (403 `attorney_not_verified`, like `verifiedCounselor`), so existing shares are paused, not revoked (only she changes her consent; `attorney-verification.ts`). Each survivor with a live share gets an activity row (`attorney.unverified`, and `attorney.reverified` if access comes back) and her share list shows *Paused*; she decides whether to revoke (test: `apps/server/src/shares.test.ts`). | High | Define a vetting procedure (bar lookup plus a call to the organization) in the partner terms. Log who verified whom and when. Re-verify periodically. |
| W8 | **Device and shoulder-surfing risk.** An abuser with device access may find the app, history, or an unlocked session. | High | Built: Quick Exit button and triple-Esc, account deletion needs her passphrase again (an open session alone can't delete everything), 12-hour session TTL, keys held in memory only, auto-lock after 15 minutes of inactivity, and a warning wherever a file is downloaded that it is not encrypted. Still to do: neutral naming and icon, clearing residue on exit, browser-history guidance. Needs advocate review. |
| W9 | **No 18+ enforcement.** NJ requires anyone to report suspected child abuse (N.J.S.A. 9:6-8.10). | Medium | **Mitigated (self-attestation only).** Survivor registration requires "I am 18 or older" (server schema `ageConfirmed18: true`, stored as a flag plus server timestamp). Anyone who says they're under 18 sees a kind message pointing to Childhelp (1-800-422-4453), RAINN (800-656-4673) and 911, and nothing is saved or sent. It cannot verify age. Partner-channel onboarding and counsel review of the wording remain. |
| W10 | **Ledger is tamper-evident, not tamper-proof.** The operator controls the head. A fully rewritten chain looks valid. The in-browser checks (`/verify`, the attorney's verification panel; W22) recompute entries and links on the reader's device, so the server's own "verified" answer is no longer trusted, but they check against the head the same operator serves, so a fully rewritten chain still passes them. | Med | Anchor the ledger head externally (RFC 3161 timestamps or a public transparency log). Publish heads regularly. |
| W11 | **Metadata exposure** (section 2). *IP / device data (weekend MVP, done):* no client IP address, user agent, referrer, request URL or query string is written by Matra's code to the database, WAL, ledger or logs. Per-client rate limits (sign-in, registration, SMS sends, attestation proxy) key on `HMAC-SHA256(salt, IP)` where the salt is 32 random bytes per UTC day, in memory only; a timer at midnight UTC zero-fills it and empties those limiters whether or not a request arrives, so an idle process does not hold yesterday's salt next to yesterday's keys; limiter windows are capped at 24 h and expired entries are swept every 10 minutes (`apps/server/src/privacy.ts`, `auth.ts RateLimiter`). Expired session rows are deleted at startup, on every sign-in and every 10 minutes (`auth.ts purgeExpiredSessions`). Request logs (app server, key holders and matcher, one shared implementation in `@matra/shared`) are `METHOD <route pattern> status ms` only; `MATRA_LOG_REQUESTS=0` turns them off. Error logs carry the error message only. Development builds (not production) log mock SMS codes with a masked number. Regression tests `apps/server/src/privacy.test.ts` (full session behind a proxy, IPv4 and IPv6, checks DB files and captured logs; midnight salt drop and session sweep with fake timers) and the matcher's log test in `apps/matcher/src/matcher.test.ts`. *No third-party requests:* CSP `'self'` only; `scripts/audit-web-build.mjs` (run by `npm run build`) fails on any unexpected host or tracker in the built app; every e2e test fails on a request to another origin. Retention per field: [PRIVACY_DATA_INVENTORY.md](PRIVACY_DATA_INVENTORY.md). **Residual:** (1) the hosting edge / load balancer logs IPs unless configured not to (DEPLOY.md), and the SMS provider keeps its own records (W19); (2) the operator can modify the server to log IPs (W4-like: code is trusted); (3) timestamps, record sizes (not padded), share graph, consent text and usernames remain (section 2); (4) per-IP limits restart at midnight UTC and are only a speed bump. (5) the dev/demo "Server view" (`MATRA_INSPECTOR=1`; `apps/server/src/inspector.ts`, holder `/debug/state`, matcher `/v1/debug/state`) keeps the last 200 request summaries (route pattern, body values cut to 48 characters, secrets the server never stores redacted; no headers, no IP) and each holder's last 20 blinded elements in memory, and serves them and every table unauthenticated: every service refuses it in production unless `MATRA_DEMO_MODE=1` (one rule, `inspectorEnabled()` in `@matra/shared`; `apps/server/src/inspector.test.ts`), and it must never run where real data is. Legal questions Q-038, Q-039. | Med | Size padding for records and blobs; coarser timestamps where the ledger does not need them; consent text only as a ledger hash if that suffices; an edge that is configured (and contractually bound) not to log IPs. |
| W12 | **Client-side RSA-OAEP with long-lived keys, no forward secrecy.** A compromised attorney private key exposes every record ever shared with that attorney. | Low–Med | Per-share keys or periodic rotation; attorney key hygiene in partner terms. |
| W13 | **Sybil matches.** The threshold counts distinct *accounts*. Accounts are cheap (self-attested 18+), and after one OPRF evaluation the tag for a target can be reused by more accounts without further evaluations (per-submission OPRF evaluation would close that; deferred, see `docs/design/PER_SUBMISSION_OPRF.md`). A forced match exposes a real survivor's contact bundle to a counselor (not to the attacker). *Decoy lines fixed (review H1):* the tag is derived from the line's intercept and every entry is opened with K_P, so Sybil entries sealed on a fake line can no longer hide real reports, and extra/foreign lines raise a counselor alert. *Mitigated (review M2):* groups are released only once the matching entries are ≥ 72 h old (`MATRA_MATCH_RELEASE_DELAY_HOURS`), and the counselor sees Sybil signals (accounts created within 24 h of each other, entries sealed < 7 days after account creation). *Phone friction (weekend MVP):* an account must confirm a phone number by SMS before it can call the OPRF or lodge an entry (`requireMatchingEligible`, 403 `phone_not_verified`), and one phone can enable at most `MATRA_SMS_MAX_ACCOUNTS_PER_PHONE` accounts (default 2; `apps/server/src/sms.ts`). This makes **cheap mass accounts** cost a phone per two accounts. It does **not** stop SIM farms, rented numbers, or someone with a few phones, and with the real provider VoIP (and every non-mobile or unchecked) number is refused by a Twilio Lookup line-type check (the mock provider used in development and demos verifies nothing). It is a server-side gate, not a cryptographic one: the app server (or whoever holds it) decides who is verified, which is W14 residual (4). Code requests are capped per account, per (account, phone), per client IP and globally, and only NANP numbers are accepted by default (`MATRA_SMS_ALLOWED_COUNTRY_CODES`), against SMS pumping that could also exhaust the provider account and switch the gate off for real survivors. The real adapter fails closed: only numbers Twilio Lookup reports as `mobile` get a code. The count is not decremented when an account is deleted (the row has no account id). Privacy cost: W19. | High | Account verification without a user list (partner invite codes, anonymous credentials issued after phone verification by a party other than the app server); counselor plausibility review before any contact; contact only on the survivor's own terms. |
| W14 | **OPRF key custody.** *Done (weekend MVP):* the additive 2-of-2 holders were replaced by a **t-of-m threshold OPRF** (Shamir over the ristretto255 scalar field, per-share DLEQ proofs, Lagrange combination in the exponent on the client; `packages/crypto/src/threshold.ts`). Each holder can run as its **own process** (`npm run -w @matra/server holder`) with one share, its own quota DB and logs; the app server relays evaluations with a 60 s Ed25519 holder token (pseudonymous subject, audience = holder index, bound to the blinded element, replay-checked until expiry; production refuses plain http to a non-loopback holder) and checks each holder's key against the pinned one at startup. Builds pin t, the group key and every share key (all or none; a production build that is not a demo fails to build without them); the client refuses inconsistent, duplicate or identity keys and names a holder whose proof fails; one holder down still seals (t of m). The server records the key set and refuses to boot on a silent change (`MATRA_OPRF_ROTATE=1` → new key epoch, clients re-seal on sign-in). **Residual:** (1) in **in-process** mode (dev, e2e, single-host demo) the operator holds every share and can test guessed identifiers offline; (2) any **t colluding holders** can do the same (they still cannot open bundles); (3) the MVP **dealer ceremony** (`oprf-ceremony`) briefly knows k; (4) holders **trust the app server** that a token subject is an eligible survivor and accept any well-formed subject, so whoever holds the app server's holder-token key (the operator, or a thief of that key) can mint a fresh subject per query and get unlimited evaluations from t honest holders: **the same power as holding k, used online instead of offline**. Remote mode only moves the operator's dictionary attack onto holders that can observe it; each standalone holder now has a global daily evaluation budget (`MATRA_HOLDER_DAILY_BUDGET`) with log alerts and an append-only table of daily totals, which makes mass querying visible and bounded but does not stop a few targeted guesses about a known suspect; (5) no separate institutions run holders yet. | High (both modes) | Eligibility attested by a party other than the app server (e.g. anonymous / Privacy Pass-style tokens issued by a separate issuer after phone and age verification and spent at the holders), so the app server cannot mint subjects; run each holder at a separate institution (remote mode, https) and have it review its daily totals; replace the dealer with a DKG (Pedersen / GJKR); HSM/KMS custody; open legal questions Q-016, Q-040, Q-041. |
| W15 | **Counselor key substitution / insider.** *One counselor per group (weekend MVP, matcher-service):* each matched group is released to ONE counselor, chosen by the matcher by state (licensed where it happened, else where a survivor lives; load-balanced; reason recorded), instead of to every verified counselor, so one insider sees only the groups assigned to her. Server-enforced: every listed counselor still holds a seal on every entry (W18). *Key substitution mitigated (review M4):* the counselor roster is signed offline with the organization's Ed25519 key (`npm run -w @matra/server sign-roster`) and builds pin its public key (`MATRA_COUNSELOR_ROSTER_PUBKEY`); clients then seal only to listed counselors with the listed key. Residual: unpinned (development and demo) builds trust the server's list; a production build that is not a demo cannot be built without the pin. *Insider:* a real counselor sees matched survivors' contact details. Seals are per-counselor and bound to the tag by AAD; counselors cannot call the OPRF or open unmatched entries. Research A7 is **mitigated, not closed**: a counselor colluding with a Sybil survivor account can seal a guess and see whether a group appears after the release delay. **Residual risk: Sybil + counselor collusion; needs account-level Sybil resistance before real use.** | High | Account-level Sybil resistance (W13); vetting and contract; org key held offline; split the counselor key (threshold decryption); log decryptions on a separate system. |
| W16 | **Magnet identifiers (review H2, fixed).** A reserved-path deny-list turned share / messenger / stories links into canonicals like `instagram:share` or `facebook:messages` that would match unrelated reports, and free-text "other" identifiers containing digits became phone numbers. Now: per-host allow-list profile parsing, `other` and names are never sealed, strict E.164/NANP and email rules, and a test-time denylist + fuzzing of >10,000 non-profile URLs. **Residual:** platforms add new URL shapes; anything unknown is refused (a gentle message asks for the profile page or @handle). | Low | Re-review the allow-lists when platforms change their URLs. |
| W17 | **Counselor-side verification limits.** The counselor can't check that a bundle's identifier matches the tag (that needs the OPRF), so a survivor-side entry naming a different identifier on the real line is only flagged (*identifier_mismatch*), and a duplicated entry is only de-duplicated by x. Bundles and labels are now padded to 1 KiB buckets. | Low | Counselor plausibility checks (ethics banner); report alerts to Matra. |
| W18 | **Matcher service (weekend MVP; `apps/matcher`).** A separate service decides which groups are released, when, and to which one counselor, from routing tags (incident state, her state) that her client seals to the matcher's attested P-256 key (ECIES; AAD binds the tag, so routing can't be moved between entries). It holds tags, entry times, account-creation hours, pseudonymous survivor references (HMAC of the tag and the account id under the app server's pepper: distinct per tag, so it cannot link one survivor's entries across tags) and the states in clear. **The attestation is SIMULATED:** the "platform" is a dev Ed25519 key held by whoever runs the matcher, and the measurement is a hash the matcher computes over its own source files (apps/matcher, packages/crypto and packages/shared sources and the lockfile; not node_modules or the runtime), so the check proves nothing about what code runs; it only exercises the protocol (client and app server both pin the platform key and the measurement, verify a fresh nonce, and refuse a mismatch; production refuses the simulated platform without `MATRA_DEMO_MODE=1`; a non-demo production web build refuses to build, and to seal, without the pins; a production matcher refuses to start without a pinned roster key; its public health endpoint carries no counts). **Residual:** (1) not attestation until a real platform verifier exists (Nitro / Confidential Space, reproducible build); (2) in-process mode (dev, e2e, single-host demo) gives the app server the matcher key, so no separation at all; (3) the app server still stores tags, so it still sees equality classes and could compute groups itself; (4) the app server could withhold a group, or serve its seals to a different listed counselor: the matcher signs each assignment, but the counselor's client does not verify the signature yet, so re-routing is undetected (the portal says only that the matcher assigned the group to her, not that nobody else has it); (5) the matcher's database and the app server's together (same operator) link states to entries; (6) assignment reasons cached by the app server name a state for each released group. Legal questions Q-017, Q-035, Q-042. | Med | Real attestation (Nitro PCR0 / Confidential Space image digest) over a reproducible build, pinned in production builds; run the matcher under a different operator than the app server; verify signed assignments in the counselor portal; seal each entry only to the assigned counselor (needs the matcher to release seals, or a threshold counselor key). |
| W19 | **Phone tokens (verify-then-forget, weekend MVP).** After a successful SMS check the server keeps only `HMAC-SHA256(MATRA_PHONE_HASH_KEY, "matra/phone-token/v1\|" + E.164)` and a count in `phone_tokens` (no user id, no timestamps, `WITHOUT ROWID`), plus `users.matching_verified = 1`. The number and the code are never written to the database or the request log; pending challenges live in memory for 10 minutes. The token count is **not** written in the same commit as her account flag: it is buffered in memory and flushed in its own transaction 10–60 min later (random), sorted with any other tokens verified meanwhile, followed by a `wal_checkpoint(TRUNCATE)`; the flag's own commit is checkpointed too.
